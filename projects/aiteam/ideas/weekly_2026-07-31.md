## Add per-tag circuit breaker for StackExchange after 20 consecutive http_status=000000 failures

**Score:** 3.600000000000000088 · **Build:** 1.5h · **Impact:** `medium` · **Slug:** `stackexchange-null-status-circuit-breaker-followup`

**Signal:** `diagnose.e_repeated_failures_14d[3] (stackexchange_fetch_failed, n=120, http_status=000000); prior_ideas[stackexchange-fetch-null-status-fix, stackexchange-null-status-circuit-breaker]`

stackexchange_fetch_failed logged 120 times in diagnose.e_repeated_failures_14d[3] this run, with the example payload showing tag=hazardous-materials and http_status='000000' — a malformed/impossible status distinct from a real 4xx/5xx server response, meaning these are transport-layer failures (DNS, TLS, connection reset) not rate-limiting or content errors. This pattern has now appeared in three consecutive weekly diagnose snapshots (stackexchange-fetch-null-status-fix and stackexchange-null-status-circuit-breaker were both proposed and remain pending, unresolved).

This is a re-proposal, not a duplicate: the prior two ideas are still sitting in operator_action='pending' with no build or rejection recorded, and the count has not meaningfully dropped (386 → 198 → 120 over three runs, still triggering the diagnose threshold every week). The idea here narrows scope to the smallest defensible fix: wrap the existing stackexchange_poll fetch call in a per-tag failure counter that persists to a flat file (tag:count), and skip the tag for the remainder of the day once the counter hits 20 consecutive failures without a success in between. This stops the poller from burning ~4 tags' worth of retry cycles daily against a server that isn't responding.

First action: add a `~/agents/scan-agent/workspace/se_failcount_<tag>.txt` counter, increment on http_status='000000', reset to 0 on any successful fetch, and add a guard clause before the fetch call that skips if count >= 20. This is a single bash function addition to the existing poll script, no new files, no schema changes.

Saves an estimated 0.5-1 operator hours/month not spent investigating recurring stackexchange noise in the diagnose report, plus removes ~100+ dead audit_log rows/week that currently obscure genuinely actionable e_repeated_failures_14d signals. If this is wrong, the cost is: a transient StackExchange outage gets misdiagnosed as a dead tag and skipped for a full day, delaying discovery of real content for that tag by up to 24 hours — recoverable by manually clearing the counter file.
